# Module 03 — Identity, Users, Roles, Permissions & Security

هذا الـModule هو **طبقة التحكم والأمان الأساسية** في Afro HR SaaS.
Module 02 يحدد *من هو الموظف داخل الهيكل التنظيمي*، بينما Module 03 يحدد:

> **من يستطيع الدخول؟ وبأي هوية؟ ولأي شركة؟ وعلى أي بيانات؟ وماذا يستطيع أن يفعل؟ ومن وافق على هذه الصلاحية؟**

وهذا مهم جدًا لأن النظام سيحتوي على بيانات شديدة الحساسية: الرواتب، National ID، العقود، التحقيقات، المستندات، الحسابات البنكية، تقييمات KPI وغيرها. الـOperations Manual نفسه ينص على أن بيانات الموظفين والتعويضات والـPayroll والتحقيقات Confidential ولا يصل إليها إلا authorized personnel، وأن العمليات يجب أن تكون traceable وقابلة للتدقيق. 

---

## 3.1 Core Identity Architecture

سنفصل بين 4 كيانات لا يجب دمجها في جدول واحد:

**Person → Employee → User Account → Access Assignments**

مثال:

```text
Ahmed Mohamed
      │
      ▼
Person
      │
      ▼
Employee
AFRO Egypt
HR Code: AF-10235
Position: Project Manager
      │
      ▼
User Account
ahmed@afro.com
+20xxxxxxxxxx
      │
      ▼
Access Assignments
Project Manager
Project A
Project B
Employee Self-Service
```

السبب أن **ليس كل Employee بالضرورة User**، كما أن الـUser قد تتغير وظيفته أو مشروعه دون إنشاء حساب جديد.

# 3.2 Multi-Company Identity Model

بما أن النظام Multi-Company SaaS، فلا يكفي:

```text
User → Role
```

بل:

```text
User
 ↓
Tenant / Company
 ↓
Role Assignment
 ↓
Scope
 ↓
Permissions
```

مثال:

```text
User: Ahmed
Company: Afro Egypt

Role:
Project Manager

Scope:
Project A
Project B
Project C

Permissions:
Employees.View
Attendance.View
Attendance.Approve
Leave.Approve
Manpower.Request
KPI.Submit
```

وبالتالي مدير المشروع يستطيع إدارة أكثر من مشروع كما اتفقنا، بدون إعطائه صلاحية على بقية مشاريع الشركة.

# 3.3 Tenant Isolation

كل شركة تعتبر **Tenant مستقل**.

```text
Platform
│
├── Afro Egypt
│   ├── Users
│   ├── Employees
│   ├── Roles
│   └── Data
│
├── Company B
│
└── Company C
```

كل Tenant يصل حتى **5,000 Employee**.

قاعدة إلزامية:

```text
Tenant A
      ✕
Tenant B
```

لا يجوز لمستخدم Company A الوصول إلى بيانات Company B حتى لو عرف:

```text
Employee ID
API Endpoint
Record ID
URL
```

ويجب تطبيق Tenant Isolation في:

```text
Database queries
APIs
Background jobs
Reports
Exports
File storage
Search
AI Copilot
Audit logs
Cache
Notifications
```

خصوصًا **AI**: لا يجوز أن يسترجع الـCopilot بيانات Tenant آخر.

# 3.4 Platform Super Admin vs Company Super Admin

هذه نقطة مهمة جدًا.

لدينا مستويان منفصلان.

### Platform Super Admin

خاص بإدارة منصة SaaS نفسها.

يستطيع:

```text
Create Tenant
Suspend Tenant
Configure Subscription
Set Limits
View System Health
Manage Platform Features
```

لكن الأفضل أمنيًا ألا يستطيع تلقائيًا قراءة:

```text
Employee salaries
National IDs
Bank details
Investigations
Contracts
Payroll
```

إلا من خلال Controlled Support Access.

### Company Super Admin

لكل شركة Super Admin مستقل كما طلبت.

مثال:

```text
AFRO Egypt
    └── Super Admin A

Company B
    └── Super Admin B
```

ولا يرى أحدهما الآخر.

# 3.8 Role-Based Access Control — RBAC

لن نعتمد على Job Title مباشرة.

أي:

```text
Position ≠ Role
```

مثال:

Position:

```text
Project Manager
```

قد يحصل على:

```text
Employee Role
+
Project Manager Role
+
Hiring Requester Role
+
KPI Evaluator Role
```

وهذا يجعل النظام مرنًا جدًا.

# 3.9 Permission-Based Model

كل Role عبارة عن مجموعة Permissions.

صيغة موحدة:

```text
Resource.Action
```

مثل:

```text
Employee.View
Employee.Create
Employee.Edit
Employee.Transfer

Attendance.View
Attendance.Edit
Attendance.Approve

Leave.View
Leave.Approve

Payroll.View
Payroll.Process
Payroll.Approve

Recruitment.Request
Recruitment.Approve

KPI.View
KPI.Submit
KPI.Approve
```

بدل Hard Coding مثل:

```text
if user == HR Manager
```

نستخدم:

```text
Can(User, "Payroll.Process")
```

# 3.11 Data Scope — أهم جزء

وجود Permission وحده خطر.

لو Project Manager لديه:

```text

```

هل يرى 5,000 موظف؟

لا.

لذلك كل Permission مرتبطة بـScope.

```text
Permission + Scope
```

الـScopes:

```text
Self
Direct Reports
Indirect Reports
Team
Department
Business Unit
Project
Multiple Projects
Location
Region
Legal Entity
Company
Custom Scope
```

مثال:

```text
Ahmed
Role: Project Manager

Employee.View
Scope:
Project Cairo
Project Alexandria
```

يرى فقط الموظفين assigned لهذه المشاريع.

# 3.12 Multiple Concurrent Assignments


لذلك:


وكل Assignment له:

```text
Company
Role
Scope Type
Scope ID
Start Date
End Date
Status
Assigned By
Approval Reference
```

# 3.18 Sensitive Field-Level Security

بعض البيانات تحتاج حماية على مستوى **الحقل نفسه**.

مثلاً Employee Profile:

```text
Name                 ✓
Position             ✓
Project              ✓
Mobile               Conditional

National ID          Restricted
Bank Account         Restricted
Salary               Highly Restricted
Medical Information  Highly Restricted
Investigation        Highly Restricted
```

مثلاً Project Manager يرى:

```text
Mohamed Ahmed
Technician
Project X
Active
```

لكن:

```text
Salary: ********
Bank Account: ********
National ID: ************
```

# 3.19 Document-Level Security


# 3.20 Approval Authority

Permission لا تعني Approval Authority تلقائيًا.

مثلاً:

```text
Salary Increase
```

قد يكون لدى HR صلاحية:

```text
SalaryChange.Create
```

لكن Approval Matrix تحدد:

```text
< 10%        → HR Manager
10–20%       → HR + BU Head
> 20%        → CEO
```

وتكون Configurable لكل Company.

# 3.23 Joiner–Mover–Leaver Security

هذه من أهم نقاط التصميم لأن الـManual يحتوي Hiring → Onboarding → Employment → Offboarding.

### Joiner

بعد إتمام الشروط:

```text
Employee Activated
        ↓
User Created
        ↓
Base Employee Role
        ↓
Position Roles
        ↓
Project Roles
```

لكن الـManual يمنع تفعيل الموظف في الأنظمة أو المشروع أو payroll قبل استكمال mandatory onboarding requirements. 

لذلك النظام يجب أن يمنع **Premature Account Activation**.

### Mover

عند:

```text
Transfer
Promotion
Project Change
Manager Change
Department Change
```

يعمل النظام:

```text
Recalculate Access
```

ويلغي الصلاحيات القديمة غير المطلوبة.

### Leaver

هذه Critical.

الـManual ينص صراحة على أن System Access يجب تعطيله بحد أقصى في آخر يوم عمل للموظف. 

لذلك:

```text
Offboarding Trigger
      ↓
Deactivate HR Account
      ↓
Revoke Sessions
      ↓
Revoke Tokens
      ↓
Remove Roles
      ↓
Disable API Access
      ↓
Notify IT
```

ويتم تسجيل كل خطوة.

# 3.31 Data Export Security


# 3.46 قاعدة Authorization النهائية

أي Request داخل النظام يمر بالمعادلة:

```text
ALLOW =
Authenticated
AND
Tenant Match
AND
Active User
AND
Permission Granted
AND
Scope Match
AND
Policy Passed
AND
No SoD Conflict
AND
Record Security Passed
```

مثلاً:

```text
Ahmed
wants
Employee.View
for Employee #245
```

النظام لا يسأل فقط:

```text
Does Ahmed have Employee.View?
```

بل:

```text
Is Ahmed authenticated?
Is Ahmed active?
Is employee #245 in same tenant?
Does Ahmed have Employee.View?
Does #245 fall inside Ahmed's scope?
Is the requested field permitted?
Is there a security restriction?
```

ثم:

```text
ALLOW / DENY
```
