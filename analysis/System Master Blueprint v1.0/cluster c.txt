تمام. الآن نصل إلى **Cluster C**، وهو أخطر جزء ماليًا في النظام لأن أي خلط بين **Compensation Master** و**Payroll Calculations** و**Approved Inputs** و**Payment Execution** سيؤدي إلى أخطاء يصعب تتبعها لاحقًا.

الـManual الحالي يحدد بوضوح أن Payroll يعتمد على employee master data، salary details، grades، employment status، project allocations، deductions/adjustments، taxes، social insurance، bank data، ثم يُرسل إلى Finance للصرف، مع Cost Reporting حسب المشروع.  كما ينص صراحة على أن Payroll لا يُعالج إلا بناءً على validated employee information وapproved project allocations وattendance records وallowances وKPI evaluations وauthorized payroll adjustments.

# 2. أهم قاعدة معمارية

هناك فرق بين:

```text
Compensation
```

و:

```text
Payroll
```

**Compensation** يقول:

> ماذا يستحق الموظف وفق عقده أو قرار معتمد؟

أما **Payroll** فيقول:

> ماذا يجب دفعه فعليًا في هذه الفترة؟

مثال:

```text
Basic Salary = 20,000
```

هذا Compensation.

لكن هذا الشهر:

```text
Basic              20,000
OT                   1,500
Field Allowance      3,000
KPI Bonus            2,000
Loan Deduction      -1,000
Unpaid Leave        -1,333
Tax                 -2,200
Social Insurance   -XXXX
```

هذه Payroll Transactions.

إذن **لا نستخدم payroll table كـsalary master**.

# 103. أهم Data Integrity Rules

أثبت القواعد التالية:

**Rule 1 — No Payroll Without Active Eligibility**

```text
employee eligible_for_payroll = true
```

وذلك يتفق مع الـManual الذي يمنع inclusion in payroll قبل استكمال متطلبات الـonboarding اللازمة. 

**Rule 2 — No Unapproved Inputs**

أي allowance أو KPI أو deduction أو salary change غير Approved:

```text
NOT PAYROLL ELIGIBLE
```

**Rule 3 — No Overlapping Compensation**

لا يوجد packageان Active للفترة نفسها بدون valid override model.

**Rule 4 — No Direct Editing After Lock**

```text
LOCKED = IMMUTABLE
```

**Rule 5 — Historical Correction Via Adjustment**

```text
old payroll ≠ edited
```

بل:

```text
retro/off-cycle adjustment
```

**Rule 6 — Financial Reconciliation Required**

Bank + Payslip + Payroll + Finance totals يجب أن تتطابق وفق reconciliation rules.


وهذا الفصل هو ما سيجعل النظام قابلًا للتدقيق والتوسع.

# القرار المعماري النهائي لـCluster C

أوصي بتثبيت القاعدة التالية:

> **Payroll Engine must never calculate directly from mutable operational data. All variable payroll data must enter through approved, traceable, period-bound Payroll Inputs. Compensation is effective-dated master data; Payroll Run is an immutable financial snapshot once approved and locked; historical corrections are handled only through retro/off-cycle adjustments.**

وهذه القاعدة متوافقة جدًا مع ما يطلبه الـManual من validated employee information، approved project allocation، attendance، allowances، KPI evaluation وauthorized adjustments قبل processing. 

وبذلك أصبح لدينا حتى الآن:

```text
Core ERD
   ↓
Cluster A
Recruitment → Onboarding → Activation

   ↓
Cluster B
Time → Attendance → Leave → Availability

   ↓
Cluster C
Compensation → Payroll → Cost → Finance
```

**الخطوة التالية المنطقية هي Cluster D — Performance Management, KPI, Learning, Competencies, Certifications, Career Management, Talent Review, Succession, Promotions & Internal Mobility ERD.**

وهذا Cluster مهم لأننا سنبني فيه لأول مرة **Talent Intelligence Chain** كاملة:

```text
Position
→ Required Competencies
→ Employee Skills
→ Objectives/KPIs
→ Performance Review
→ Skill Gaps
→ Development Plan
→ Training
→ Certification
→ Talent Review
→ Nine Box
→ Succession
→ Promotion
→ Internal Mobility
→ New Assignment
→ Compensation Change
```

مع فصل واضح بين **facts** مثل Performance Score وSkill Assessment وبين **decisions** مثل Promotion وSuccession Nomination، حتى لا يتحول النظام إلى ترقية الموظف تلقائيًا بناءً على Score فقط.
