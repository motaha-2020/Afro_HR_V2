تمام. نبدأ الآن من قلب النظام نفسه، لأن أي خطأ هنا سينتقل لاحقًا إلى Payroll وAttendance وRecruitment وPerformance وباقي الـModules.

سأبنيها كـ **Logical Database Schema + Core ERD v1.0** للنواة التالية:

**Tenant → Company → Organization Unit → Job → Position → Employee → Employment → Assignment → Contract → Compensation**

وسأحافظ على القاعدة الأساسية: **كل كيان له Owner واحد، والبيانات التاريخية لا تُستبدل بل تُؤرشف باستخدام effective dating.**

الـManual يدعم هذه البنية؛ فهو يربط الموظف بـPosition وProject وDirect Manager وWork Location وSalary وJoining Date، ثم يستخدم نفس البيانات في Onboarding وPayroll وHR Operations وOffboarding.  كما أن الهيكل التنظيمي الحالي يوضح فصل المسؤوليات بين OD وPersonnel وPayroll وHR Operations وTalent Acquisition، وهو ما يدعم فصل الـData Domains وعدم دمجها في جداول ضخمة. 

# 1. Core ERD — المستوى الأعلى

```text
TENANT
  │
  └──< COMPANY
         │
         ├──< ORGANIZATION_UNIT
         │        │
         │        └──< POSITION
         │                │
         │                └── JOB
         │
         └──< EMPLOYEE
                 │
                 └──< EMPLOYMENT
                         │
                         ├──< ASSIGNMENT
                         │       ├── POSITION
                         │       ├── ORG UNIT
                         │       └── PROJECT
                         │
                         ├──< CONTRACT
                         │
                         └──< EMPLOYEE_COMPENSATION
```

والعلاقات الرئيسية:

```text
Tenant       1 ─── N Company

Company      1 ─── N Organization Unit

Job          1 ─── N Position

Org Unit     1 ─── N Position

Employee     1 ─── N Employment

Employment   1 ─── N Assignment

Position     1 ─── N Assignment over time

Employment   1 ─── N Contract

Employment   1 ─── N Compensation Record
```

# 42. أهم Data Integrity Rules

## Rule 1

لا يمكن أن يكون Employment تابعًا لشركة خارج Tenant الموظف.

## Rule 2

لا يمكن Assignment أن يشير إلى Position من Company أخرى إلا في حالة Secondment مصرح بها.

## Rule 3

إجمالي Project Allocation للموظف لا يتجاوز:

```text
100%
```

إلا إذا Configuration يسمح بذلك.

## Rule 4

لا يوجد أكثر من:

```text
ONE PRIMARY ASSIGNMENT
```

فعال في نفس الفترة لنفس Employment.

## Rule 5

لا يجوز وجود عقدين Active متداخلين إلا إذا نوع العقد يسمح بذلك.

## Rule 6

لا يجوز وجود Compensation packages متداخلة زمنيًا لنفس pay basis بدون سبب معتمد.

# 43. Temporal Overlap Prevention

هذه من أهم قواعد قاعدة البيانات.

مثال:

```text
Salary A
01-Jan → 31-Mar

Salary B
15-Mar → Current
```

هناك overlap.

يجب منعها.

PostgreSQL يمكنه دعم ذلك باستخدام:

```text
EXCLUDE CONSTRAINT
```

مع date ranges.

وهذه ميزة قوية جدًا نستخدمها في:

```text
Assignments
Compensation
Contracts
Reporting Lines
Grade Assignment
```

# 47. Optimistic Locking

نضيف:

```text
version INT
```

للجداول الحساسة.

مثال:

مستخدمان يفتحان نفس Compensation.

User A يعدله.

User B يعدل نسخة قديمة.

بدل overwrite صامت:

```text
409 Conflict
```

ويطلب Refresh.

# 48. Referential Delete Rules

لا نستخدم Cascade Delete بشكل واسع.

مثال:

```text
Employee
```

لا يجوز حذفه لأن له Payroll.

لذلك:

```text
ON DELETE RESTRICT
```

غالبًا.

بينما جداول configuration الفرعية قد تستخدم:

```text
ON DELETE CASCADE
```

بحذر.

# 64. قبل الانتقال لباقي Modules

هناك خمسة قرارات Database يجب أن نثبتها الآن:

**1. Person vs Employee:** أوصي حاليًا باستخدام `employee` كـCore Entity، وإذا توسع النظام لاحقًا ليشمل candidates/external workers بعمق يمكن إدخال `person` abstraction.

**2. Organization Hierarchy:** جدول واحد recursive `organization_units`، وليس table لكل level.

**3. Job vs Position:** فصل كامل ولا رجوع عنه.

**4. Employee vs Assignment:** Project/Location/Manager لا تعيش داخل Employee.

**5. Salary:** Effective-dated component model، وليس salary columns داخل employee.

هذه القرارات الخمسة ستحدد جودة النظام بدرجة كبيرة.

## الخطوة التالية

الآن لدينا **Core Logical ERD**. الترتيب المنطقي التالي هو استكمال الـERD حول هذه النواة، لكن **بـModule Clusters** بدل القفز إلى جميع الجداول مرة واحدة:

**Cluster A — Recruitment → Onboarding → Personnel/Documents → Employee Activation**

ثم:

**Cluster B — Attendance → Shift/Roster → Leave → Availability**

ثم:

**Cluster C — Compensation → Payroll → Allowances → KPI Payment → Cost Allocation**

ثم Talent / Performance / Learning / ER / Service Desk / Offboarding.

وأرى أن نبدأ مباشرة بـ **Cluster A ERD: Recruitment → Candidate → Offer → Onboarding → Employee Creation → Documents → Contract → Activation**؛ لأنه سيحدد بالضبط اللحظة التي تتحول فيها بيانات الـCandidate إلى Golden Employee Record، وهي واحدة من أخطر نقاط الـduplication في أي HR system.
