تمام. **Cluster P** هو طبقة **Enterprise Discovery & Knowledge Access** التي تمنع تكرار البحث داخل كل Module، وتبني نقطة وصول موحدة للبيانات والوثائق والمهارات والهيكل التنظيمي والمحتوى المعرفي، مع احترام الصلاحيات في كل خطوة.

المبدأ الحاكم هنا:

> **Search Index ليس System of Record.**
> هو نسخة قابلة للبحث من البيانات المصرح بفهرستها، بينما المصدر الحقيقي يظل داخل الـDomain الأصلي.

وده مهم لأن النظام عندنا أصبح يحتوي Employee Core وOrg Structure وRecruitment وLearning وER وHSE وDocuments وAnalytics وغيرها، وكلها تنتج معلومات يحتاج المستخدم أن يصل إليها بسرعة. كما أن الهيكل الحالي نفسه موزع بين Talent Acquisition وPersonnel وPayroll وER & Compliance وHR Operations وغيرها، وبالتالي البحث يجب أن يعكس صلاحيات كل وظيفة لا أن يفتح كل المحتوى للجميع.

# 1. Search Architecture

المسار الصحيح:

```text
Business Domains
A → O
   |
   | Events / CDC
   v
Search Ingestion
   |
   v
Search Normalization
   |
   +---------+---------+
   |                   |
   v                   v
Text Index         Vector Index
   |                   |
   +---------+---------+
             |
             v
      Unified Search API
             |
      +------+------+------+
      |      |      |      |
      v      v      v      v
    Web   Mobile   BI    AI Copilot
```

# 2. لا يوجد Search مباشر على Production DB

لا أريد:

```text
Search Employee
→ SELECT LIKE '%Ahmed%'
```

على operational tables.

الأفضل:

```text
EmployeeUpdated Event
      ↓
Search Indexer
      ↓
Employee Search Document
```

ثم الـSearch Service يستعلم من الـIndex.

> ما المستندات المطلوبة للتعيين؟

RAG لا يخترع إجابة.

يسترجع من approved policy/manual.

والـManual الحالي يحتوي بالفعل required onboarding documents ومتطلبات contracting/HSE/activation، وبالتالي هذا النوع من المحتوى مناسب جدًا لـpermission-aware policy retrieval.

# 50. Search vs Knowledge Graph vs RAG

مهم جدًا عدم خلطهم:

### Search

```text
Find documents / entities
```

### Knowledge Graph

```text
Understand relationships
```

### RAG

```text
Retrieve trusted content for AI answers
```

مثال:

```text
Search:
Find Ahmed

Graph:
Who manages Ahmed?

RAG:
What policy governs Ahmed's project deployment?
```

# 77. أهم Architectural Rules

هذه أعتبرها Non-Negotiable:

1. **Search Index ليس System of Record.**
2. Search لا تكتب Business Data.
3. كل Result يخضع لـTenant Isolation.
4. Permission trimming يجب أن يحدث قبل إرجاع النتيجة.
5. Restricted content لا يدخل General Search Index.
6. Search security ليست UI filtering فقط.
7. Index updates يجب أن تكون event-driven حيثما أمكن.
8. Security changes يجب أن تحدث لها reindex سريع.
9. RAG لا يقرأ raw production DB مباشرة.
10. RAG retrieval يجب أن يكون permission-aware.
11. AI لا يحصل على جميع documents بسبب وجودها في Vector DB.
12. Embeddings تعتبر data ويجب حمايتها.
13. Medical وER content تحتاج security zones مستقلة.
14. Semantic similarity لا تعني business truth.
15. Structured authoritative data لها أولوية على semantic content.
16. AI-derived relationships تظل unverified حتى اعتمادها.
17. Policies يجب أن تدعم versions وeffective dates.
18. AI answers على policy/process يجب أن تستخدم current approved version افتراضيًا.
19. Search history نفسها قد تكون sensitive.
20. Search logs يجب أن تمنع تسريب PII.
21. Bulk export يحتاج governance منفصل.
22. Deep link يعيد authorization check في الـsource module.
23. Deleted records يجب إزالتها من search/vector indexes.
24. Tenant data يجب ألا تختلط في vector retrieval حتى لو similarity عالية.
25. Hybrid retrieval أفضل من vector-only retrieval لمعظم HR use cases.

# 78. الفرق بين Cluster P والـClusters الأخرى

```text
Cluster A–J
Own business facts.

Cluster O
Own documents/files/records.

Cluster M
Own analytics/metrics.

Cluster P
Own searchable representations,
knowledge relationships,
indexes,
embeddings,
retrieval metadata.
```

مثال:

```text
Employee Skill

Cluster F:
owns skill assignment.

Cluster P:
indexes and relates the skill
for search and knowledge retrieval.
```

ومثال:

```text
Employment Contract

Cluster O:
owns the document.

Cluster P:
indexes permitted metadata/text
and makes it discoverable.
```

# 79. وضع الـArchitecture بعد Cluster P

أصبح لدينا:

```text
A–J
Business Domains

K
Integration & Data Governance

L
Configuration / SaaS Control Plane

M
Analytics / BI / AI

N
API / Events / Runtime Backbone

O
Documents / Records / Evidence

P
Enterprise Search / Knowledge / RAG
```

وبعد Cluster P، النظام لم يعد فقط قادرًا على **تخزين وتشغيل البيانات**، بل أصبح قادرًا أيضًا على **العثور عليها، ربطها ببعضها، فهم علاقتها، واسترجاعها بشكل آمن لخدمة المستخدم والـAI**.

**الخطوة التالية المنطقية الآن هي Cluster Q — Enterprise AI Platform, AI Copilot, Agent Runtime, Prompt Registry, Model Gateway, Model Routing, Tool Registry, AI Permissions, Human-in-the-Loop, AI Audit, Evaluation, Guardrails, Cost Control, Conversation Memory, Agent Tasks & AI Governance ERD**؛ لأننا بعد Cluster M جهزنا analytical intelligence، وبعد P أصبح لدينا permission-aware retrieval، لكن ما زلنا لم نبنِ الطبقة التي تدير الـAI نفسه كمنصة مؤسسية قابلة للرقابة بدل وضع chatbot منفصل داخل كل Module.
