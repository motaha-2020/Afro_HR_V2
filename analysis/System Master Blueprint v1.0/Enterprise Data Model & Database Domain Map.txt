ممتاز. نبدأ الآن بـ **Enterprise Data Model & Database Domain Map**؛ وهي أهم مرحلة قبل تصميم الـBackend، لأن هدفها أن تجعل كل كيان Business Entity له **مكان واحد واضح، Owner واحد، ومصدر حقيقة واحد**، بينما بقية الـModules تشير إليه بدل أن تنشئ نسخًا منه.

الـOperations Manual نفسه يؤكد هذا الاحتياج؛ فمثلًا الـonboarding يمر بإنشاء employee profile وHR Code وPayroll registration وsystem access، ثم نفس الموظف يُستخدم لاحقًا في HR Operations وPayroll وOffboarding. لو خزّنت كل وحدة Employee مستقلًا، سنحصل سريعًا على سجلات متعارضة.  كما أن الهيكل التنظيمي الحالي يفصل المسؤوليات بين Personnel وPayroll وHR Operations وTalent Acquisition وER & Compliance وOD، لذلك يجب أن ينعكس هذا الفصل أيضًا في Data Ownership. 

# Afro_HR_V2

# Enterprise Data Model & Database Domain Map — v1.0

---

# 1. المبدأ الحاكم

لا نصمم قاعدة البيانات وفق Screens.

ولا وفق Modules فقط.

بل وفق:

> **Business Domains → Aggregate Roots → Entities → Transactions → Events**

مثال:

```text
Employee
```

ليس جزءًا من Payroll.

وليس جزءًا من Attendance.

وليس جزءًا من Performance.

هو Entity مركزي داخل:

```text
Core HR Domain
```

ثم:

```text
Payroll → employee_id
Attendance → employee_id
Performance → employee_id
Learning → employee_id
Case Management → employee_id
```

ولا يحتفظ أي منهم بنسخة أخرى من الموظف.

# القرار المعماري الذي أريد تثبيته

من هذه اللحظة أعتبر أن **Afro_HR_V2 Data Architecture** يجب أن تعتمد:

**Domain-oriented relational architecture باستخدام PostgreSQL + strict data ownership + effective dating + immutable audit + event-driven integration + shared document/workflow/rules engines.**

ولا أنصح حاليًا بـMicroservices Database-per-Service؛ لأن ذلك سيزيد تعقيد التطوير والتشغيل دون فائدة حقيقية في المرحلة الأولى. الأفضل أن نبدأ بـ:

```text
Modular Monolith
        +
Domain-separated PostgreSQL Schemas
        +
Event Bus abstraction
```

بحيث نستطيع مستقبلًا استخراج أي Domain إلى Microservice بدون إعادة تصميم الـBusiness Model.

**الخطوة التالية التي أنصح بها الآن:** تحويل هذا الـDomain Map إلى **Logical Database Schema & ERD**، ونبدأ تحديد الجداول الفعلية والمفاتيح والعلاقات `1:1 / 1:N / N:M` والـFKs، بدءًا من قلب النظام:

**Tenant → Company → Organization Unit → Job → Position → Employee → Employment → Assignment → Contract → Compensation.**

وبمجرد تثبيت هذه النواة، يصبح بناء بقية Modules أكثر أمانًا بكثير.
