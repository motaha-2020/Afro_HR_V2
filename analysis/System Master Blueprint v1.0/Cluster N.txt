بالضبط. **Cluster N** هو الـruntime backbone الذي يمنع النظام من التحول إلى مجموعة Modules مرتبطة ببعضها بشكل مباشر ومعقد.

الفكرة الأساسية هنا:

> **كل Domain يملك بياناته ومنطقه، ويتعامل مع بقية النظام عبر Contracts واضحة: APIs + Events + Commands + Background Jobs، وليس من خلال القراءة أو الكتابة المباشرة في جداول Domain آخر.**

وده مهم جدًا عندنا لأن العمليات الحالية نفسها cross-functional بطبيعتها: onboarding مثلًا ينتقل بين Talent Acquisition وPersonnel وIT وHSE وOperations، وoffboarding يحتاج Personnel وIT وFinance وDirect Manager، بينما Payroll يعتمد على بيانات معتمدة من عدة مصادر.


# 10. Transactional Outbox

هذه نقطة critical.

مثال:

الموظف أصبح Active.

لو نفذنا:

```text
1 Update Employee = ACTIVE
2 Send Event
```

قد يحدث:

```text
DB succeeded
Bus failed
```

فتصبح البيانات active لكن Payroll لا يعرف.

الحل:

```text
Employee Transaction
   |
   +--- Update Employee
   +
   +--- Insert Outbox Event
           SAME DB TRANSACTION
```


# 49. قرار معماري مهم: Microservices الآن أم لا؟

هنا أريد أن أحذر من افتراض شائع:

> وجود Event Bus وAPI Gateway لا يعني أننا يجب أن نحول كل Module إلى Microservice الآن.

بالنسبة لهذا النظام، أوصي مبدئيًا بـ:

```text
Modular Monolith
+
Clear Domain Boundaries
+
Internal Event Bus
+
Outbox Pattern
+
API Contracts
```

ثم نفصل Microservices فقط عندما يوجد سبب حقيقي مثل:

```text
Independent scaling
Independent deployment
Different security boundary
High throughput
External integration isolation
Different release cycle
```

أول Services قد تستحق الفصل مستقبلًا:

```text
Identity
Notifications
Integration Gateway
Document Processing
Analytics
AI
```

بينما تقسيم:

```text
Employee
Position
Assignment
Leave
Attendance
```

إلى عشرات microservices من البداية غالبًا سيزيد التعقيد أكثر مما يحله.

# 50. Runtime Golden Rules

أعتبر هذه القواعد إلزامية:

1. **No cross-domain database writes.**
2. No service reads another domain database directly.
3. Every event has a schema and version.
4. Financial write operations require idempotency.
5. Transactional state change + event publication use Outbox.
6. Consumers use Inbox/Deduplication where duplication matters.
7. Long-running business processes use Saga, not distributed DB transactions.
8. External webhooks are signed and replay-protected.
9. Secrets never live in source code or plaintext configuration.
10. Every request/event/job has correlation ID.
11. Retry only retryable failures.
12. Poison messages go to DLQ.
13. Replaying financial/business-critical events requires governance.
14. Logs must not expose sensitive HR data.
15. Runtime observability must include Logs + Metrics + Traces.
16. Tenant context must propagate securely through every async message.
17. Integration outages must degrade gracefully where the business permits.
