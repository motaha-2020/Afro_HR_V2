ممتاز. **Cluster M** هو الطبقة التي تفصل بين **تشغيل الـHR يوميًا** وبين **التحليل واتخاذ القرار**.
القاعدة الأساسية هنا:

> **OLTP يدير العمليات. Analytical Platform يدير الأسئلة، المؤشرات، الاتجاهات، التنبؤ، والقرارات.**

ولا أنصح إطلاقًا أن يقرأ Power BI أو Executive Dashboard مباشرة من جداول Payroll / Attendance / Employee operational tables إلا في حالات محدودة جدًا.

الـOperations Manual نفسه يثبت أن عندنا دورات زمنية وتقارير دورية واضحة في Payroll، Allowances وKPI، إضافةً إلى project cost allocation وongoing workforce management؛ وهذا يجعل وجود طبقة تحليل مستقلة أمرًا منطقيًا وليس إضافة تجميلية.  كما أن الهيكل الحالي يفصل Payroll وPersonnel وHR Operations وTalent Acquisition وER/Compliance وOD، وبالتالي سنحتاج Analytical Security تمنع أن يرى كل فريق كل المؤشرات أو البيانات الحساسة لمجرد أنها موجودة في نفس الـBI platform. 

# Cluster M — Enterprise Analytics & Intelligence Architecture

أقسمه إلى 15 Sub-Domains رئيسية:

```text
M1   Analytical Source Registry
M2   Ingestion & CDC
M3   Raw / Bronze Layer
M4   Standardized / Silver Layer
M5   Data Warehouse / Gold Layer
M6   Conformed Dimensions
M7   Fact Model
M8   KPI & Semantic Layer
M9   Dashboard & BI Catalog
M10  Analytical Security
M11  Data Lineage
M12  Data Quality for Analytics
M13  AI/ML Feature Store
M14  Forecasting / Models / Scoring
M15  Analytics Operations & Governance
```

---

# 1. أهم Architectural Principle

المسار يكون:

```text
HR Operational Database
Clusters A → L
        |
        v
CDC / Events / ETL / ELT
        |
        v
Raw / Bronze
        |
        v
Standardized / Silver
        |
        v
Warehouse / Gold
        |
        +-------------------+
        |                   |
        v                   v
 Semantic / KPI          Feature Store
        |                   |
        v                   v
 BI / Dashboards        AI / ML Models
```

وليس:

```text
Power BI
   |
   v
Payroll Production DB   ❌
```

# 38. قواعد معمارية لا أنصح بالتنازل عنها

### Rule 1

لا يوجد Executive Dashboard يقرأ مباشرة من OLTP.

### Rule 2

كل KPI له تعريف وOwner وVersion.

### Rule 3

أي Financial KPI يجب أن يعرض:

```text
Data As Of
Source
KPI Version
```

### Rule 4

PII لا تنتقل تلقائيًا إلى Warehouse.

### Rule 5

Medical / ER / Investigation data لا تدخل General BI.

### Rule 6

Project Managers يرون projects المصرح بها فقط.

### Rule 7

Historical analysis يعتمد SCD وليس current master.

### Rule 8

ML features يجب أن تكون governed وقابلة للتتبع.

### Rule 9

AI Copilot يستعلم من Semantic Layer وليس raw tables.

### Rule 10

أي Export حساس يجب أن يسجل في Audit.

**الخطوة التالية التي أراها منطقية الآن ليست Cluster Business جديد مباشرة، بل Cluster N — Enterprise API Gateway, Event Bus, Domain Events, Webhooks, Service-to-Service Contracts, Background Processing, Idempotency, Distributed Transactions, Integration Security & Observability ERD**؛ لأننا صممنا حتى الآن الـbusiness domains والـconfiguration والـanalytics، لكن ما زلنا نحتاج الـtechnical runtime backbone الذي يربط كل هذه الـdomains بطريقة scalable ويمنع الـmodules من الارتباط المباشر ببعضها.
