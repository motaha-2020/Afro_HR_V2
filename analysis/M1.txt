تمام، نبدأ بالـ **Module 01 — Platform, Multi-Company & Tenant Management** لأنه الأساس الذي سيبنى عليه كل شيء بعده.

## الهدف من الموديول

الموديول مسؤول عن فصل الشركات عن بعضها بالكامل داخل نفس المنصة، مع إمكانية تشغيل النظام داخليًا الآن ثم تحويله مستقبلًا إلى SaaS بدون إعادة بناء الـarchitecture.

الفكرة الأساسية:

```text
Platform
   ↓
Tenant / Company
   ↓
Business Units / Departments / Projects / Users / Employees
```

كل شركة لها بياناتها وسياساتها وصلاحياتها وإعداداتها الخاصة، ولا يمكن لأي مستخدم في شركة رؤية بيانات شركة أخرى إلا إذا كان من مستوى Platform Administration.

## مستويات الإدارة

سيكون عندنا مستويان إداريان منفصلان.

**Platform Super Admin** مسؤول عن المنصة ككل، ويستخدم غالبًا من مالك النظام مستقبلًا. يستطيع إنشاء شركة جديدة، تعطيلها، تحديد limits، إدارة إعدادات المنصة، متابعة حالة الخدمات، وإدارة الاشتراكات مستقبلًا.

**Company Super Admin** مسؤول فقط عن شركته، ويستطيع إدارة المستخدمين، الأقسام، السياسات، المشاريع، الصلاحيات، والـsettings داخل Tenant الخاص به.

مهم جدًا: Platform Admin لا يحصل تلقائيًا على صلاحية قراءة رواتب أو ملفات الموظفين داخل الشركات. لو احتجنا Support Access مستقبلًا يكون Access مؤقت ومراقب في Audit Log.

# إعدادات اللغة

كل Tenant يستطيع تحديد:

```text
Default Language
Arabic / English / French
```

بالإضافة إلى:

```text
Enabled Languages
☑ Arabic
☑ English
☑ French
```

لو Default = Arabic:

```text
direction = RTL
```

أما English وFrench:

```text
direction = LTR
```

ولا نربط الاتجاه بالـCompany فقط، بل بالـUser Preference أيضًا.

يعني الشركة Default Arabic، لكن موظف معين ممكن يختار English.

# Employee Limit

بما أنك حددت حتى 5,000 موظف لكل شركة، نصمم النظام مبدئيًا على:

```text
Recommended Tenant Capacity:
5,000 Active Employees
```

لكن لا أريد Hard Limit في الـdatabase.

الأفضل:

```text
max_employees = configurable
```

بحيث ممكن Tenant يكون:

500

5,000

20,000

لاحقًا.

# Tenant Isolation

دي أهم نقطة تقنية في الموديول.

كل البيانات الأساسية يجب أن تحتوي:

```text
TenantId
```

مثلاً:

```text
Employee
---------
Id
TenantId
HRCode
Name
...
```

ونفس الشيء:

```text
Project
Department
Payroll
Attendance
Leave
User
Role
Workflow
```

ومن ثم كل Query يمر تلقائيًا على Tenant Filter.

مثلاً:

```text
WHERE TenantId = CurrentTenant
```

المطور لا يفترض أنه يتذكر إضافة TenantId في كل Query؛ لازم يكون فيه حماية مركزية في الـbackend.

# HR Code Uniqueness

عندنا قرار مهم هنا.

لا نحتاج HR Code يكون Unique على مستوى المنصة كلها.

يكفي:

```text
TenantId + HRCode = Unique
```

مثلاً:

شركة A:

```text
HR Code = 10025
```

وشركة B يمكن يكون عندها أيضًا:

```text
HR Code = 10025
```

بدون مشكلة.

# أهم Business Rules

أقترح نثبت القواعد دي من الآن:

1. أي Record Business يجب أن يتبع Tenant واحد.
2. لا يوجد User Business بدون Tenant إلا Platform User.
3. Company Super Admin لا يرى Tenant آخر.
4. HR Code unique داخل Tenant.
5. حذف Tenant ممنوع مباشرة.
6. تغيير إعداد حساس يسجل Audit.
7. كل Module يمكن تفعيله أو تعطيله.
8. Language preference تكون User-level مع Company default.
9. Payroll/Attendance/AI policies تكون Tenant configurable.
10. كل Integration يتبع Tenant محدد.

# قرار Architecture مهم

أنا لا أنصح في البداية بـ:

```text
Database per Company
```

لكل Tenant.

الأفضل للمرحلة الحالية:

```text
Shared PostgreSQL
+
TenantId isolation
+
Application Security
+
PostgreSQL Row-Level Security where appropriate
```

وبعد ذلك يمكن دعم:

```text
Dedicated Database Tenant
```

للعملاء الكبار أو أصحاب المتطلبات الأمنية الخاصة.

ده يجعل المنتج عنده مستقبلًا:

```text
Standard Tenant
Enterprise Dedicated Tenant
```

## Definition of Done للموديول

نعتبر Module 01 مقفول عندما نستطيع عمليًا تنفيذ السيناريو ده:

```text
Platform Admin
↓
Creates Afro Egypt
↓
Defines Arabic as default
↓
Enables HR + Attendance + Payroll + AI
↓
Creates Company Super Admin
↓
Super Admin logs in
↓
Sees only Afro Egypt
↓
Configures company
↓
Creates users later
↓
No data can cross Tenant boundary
```

لو السيناريو ده ناجح أمنيًا ووظيفيًا، نكون بنينا قاعدة النظام صح.

**التالي هو Module 02 — Organization Structure & Job Architecture**، وهنا هنبدأ ندخل بعمق في Company → Business Unit → Sector → Department → Project → Site، والـPositions والـGrades والـReporting Lines، وكيف الموظف يكون له Administrative Manager وFunctional Manager وأكثر من Project في نفس الوقت.
