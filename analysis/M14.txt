تمام. **Module 14 منطقي جدًا بعد Module 13**، وأنا أوافق على الفصل الوظيفي الذي اقترحته تحديدًا: لا يجب أن يصبح **Employee Relations / Case Management** صندوقًا لكل طلب HR يومي.

الـOperations Manual الحالي بالفعل يضع ضمن HR Operations نشاط **“Handle employee requests / Resolve HR operational issues / Coordinate with support departments”**، لكن بدون Service Catalog واضح، Ticket Lifecycle، SLA Engine، Routing أو Employee Self-Service.  كما أن الهيكل الحالي يفصل عمليًا بين **HR Operations، Personnel، Payroll، وER & Compliance**، وبالتالي يمكن للنظام توجيه كل نوع طلب إلى الـowner الصحيح بدل تجميع كل شيء عند شخص واحد. 

# Module 14 — HR Service Desk, Employee Requests, Letters, Documents & Employee Self-Service

## 14.1 الهدف الأساسي

إنشاء **Single HR Service Entry Point** لكل موظف ومدير.

الموظف لا يحتاج أن يعرف:

> هل أذهب إلى Personnel؟
> Payroll؟
> HR Operations؟
> ER؟
> Administration؟

هو فقط يختار:

> **I Need HR Help / طلب خدمة من الموارد البشرية**

**Request → Classification → Routing → SLA → Processing → Approval → Fulfillment → Employee Confirmation → Closure**

مع الاحتفاظ بخط فصل واضح:

**Normal HR Request → Module 14**

بينما:

**Complaint / Grievance / Harassment / Misconduct / Formal Dispute / Investigation → Module 13**

يرى Project / Operational HR Requests الخاصة بنطاقه.

### Personnel

يرى:

* Employee Data
* Documents
* Contracts
* Letters
* Insurance records

### Payroll

يرى:

* Payroll requests
* Compensation related items

### ER & Compliance

يرى requests المحالة رسميًا له.

### HR Manager

Cross-functional visibility حسب policy.

### Super Admin

System configuration، وليس بالضرورة business confidential content.

**System Admin ≠ Permission to read every HR Case.**

# 14.66 أهم Business Rules

أضع هنا مجموعة Rules أعتبرها أساسية من أول نسخة:

**BR-14-01**
كل request يجب أن يكون له unique number.

مثلاً:

`HRREQ-2026-000154`

**BR-14-02**
كل request يجب أن يكون له owner.

**BR-14-03**
SLA يبدأ عند submission أو receipt حسب configuration.

**BR-14-04**
لا يجوز تعديل Employee Master Data مباشرة من ticket دون approval workflow.

**BR-14-05**
كل مستند Employee يجب أن يكون version-controlled.

**BR-14-06**
لا يجوز حذف attachment بعد استخدامه في approved transaction؛ يمكن archive فقط.

**BR-14-07**
Formal grievance لا يتم التعامل معها داخل general service desk.

**BR-14-08**
عند تحويل request إلى Module 13، تطبق ER confidentiality automatically.

**BR-14-09**
Payroll request لا يستطيع Module 14 تعديل Payroll Calculation مباشرة.

**BR-14-10**
Agent لا يستطيع إغلاق request بدون Resolution Code.

**BR-14-11**
كل SLA breach يجب أن يسجل.

**BR-14-12**
Employee يجب أن يستطيع تتبع request status ما لم تكن restricted.

**BR-14-13**
كل Auto-generated letter يجب أن يحمل unique verification reference.

**BR-14-14**
Admin technical access لا يعني access إلى confidential HR content.

# 14.69 العلاقة مع الـManual الحالي

Module 14 لا يخترع وظيفة بعيدة عن الـManual؛ هو يحول جزءًا موجودًا حاليًا بصورة عامة إلى Operating System واضح.

الـManual الحالي ينص في HR Operations على:

* Handle employee requests.
* Resolve HR operational issues.
* Coordinate with support departments.
* Support employee engagement. 

كما ينص على متابعة employee records والـdocuments والـinsurance والـcontract renewals. 

نحن فقط نحول ذلك من:

> Emails + Calls + WhatsApp + Excel + Personal Follow-up

إلى:

> **Service Catalog + ESS + Ticketing + Routing + SLA + Workflow + Documents + Audit + Analytics**

# 14.70 أهم قرار معماري في Module 14

هناك نقطة أعتبرها أساسية جدًا:

**Module 14 يجب ألا يصبح Owner لكل عمليات HR.**

هو:

> **Front Door + Orchestration Layer**

وليس:

> **System of Record لكل شيء.**

بالتالي:

```text
Payroll truth          → Module 09
Attendance truth       → Module 07
Leave truth            → Module 08
Employee Core truth    → Module 01
Documents truth        → Employee Document Repository
Learning truth         → Module 11
Career truth           → Module 12
ER Cases truth         → Module 13
```

بينما Module 14 يجيب:

> **ماذا طلب الموظف؟ أين ذهب الطلب؟ من مسؤول عنه؟ متى يجب إنهاؤه؟ ماذا حدث؟ وهل تم حل المشكلة؟**

وهذه المعمارية ستمنع تكرار البيانات بشكل كبير.

## النتيجة بعد Module 14

وصلنا الآن تقريبًا إلى Employee Lifecycle متكامل جدًا:

**01** Employee Core
→ **02** Organization & Job Architecture
→ **03** Identity / Roles / Security
→ **04** …
→ **05** Recruitment & ATS
→ **06** Onboarding & Activation
→ **07** Attendance / Shifts / Field Workforce
→ **08** Leave & Availability
→ **09** Payroll & Compensation
→ **10** Performance Management
→ **11** Learning / Competency / Certification
→ **12** Career / Talent / Succession / Mobility
→ **13** Employee Relations / Grievances / Investigations
→ **14** **HR Service Desk / ESS / Requests / Letters / Documents**

والـModule الذي أراه منطقيًا بعد ذلك هو **Module 15 — Employee Documents, Contracts, Personnel Administration, Social Insurance, Medical Insurance & Compliance Management** لكن بشرط أن نفصله عن Module 14: **Module 14 يستقبل الطلب ويُدير الخدمة، بينما Module 15 يصبح الـsystem of record لكل Personnel Administration والوثائق القانونية والتعاقدية والتأمينات والتجديدات والـexpiry compliance**. وهذا مناسب جدًا لأن الـManual الحالي يعطي Personnel مسؤوليات كبيرة في هذه المنطقة لكنها ما زالت موزعة بين onboarding وHR Operations وoffboarding.
